## 0. 一句话定义

**不做"又一个书签存储服务"，做 Chrome 原生书签树的视图层与治理层。**

数据只有一个真源——Chrome 自己的书签树。扩展负责把它**呈现得更好、搜索得更准、治理得更省力**，所有变更都写回原生书签树。

---

## 1. Problem Statement

**问题**：浏览器书签是一个"只进不出"的仓库。收藏这个动作发生在"我以后会看"的瞬间，但没有任何机制让这些内容重新浮出水面。结果是**收藏即埋葬**——用户攒了 500 个书签，真正回头用的不到 20 个，而 Chrome 自带的 `chrome://bookmarks` 只有一棵树和一个精确匹配的搜索框，既不能告诉他"哪些已经死了"，也不能帮他"把这三条重复的合并掉"。

**谁在痛、多频繁**：

| Persona | 画像 | 痛点强度 | 频率 |
|---|---|---|---|
| **知识工作者**（设计 / 研发 / 产品） | 200–2000 条书签，按主题分 10–40 个文件夹 | 高——找不回来是每天的摩擦 | 每天 3–10 次 |
| **通用浏览器用户** | 50–300 条，大部分堆在书签栏，溢出后不再管 | 中——不觉得是问题，直到书签栏失效 | 每周 1–3 次 |

**不解决的代价**：
- **对用户**：书签资产持续贬值。越攒越多、越难用、越不敢删（怕删掉以后要用）。用户被迫退化成"用浏览历史当书签"，而历史 90 天就没了。
- **对产品**：书签是浏览器侧**忠诚度最高**的数据资产之一——它记录的是用户在意的站位，且天然跨设备同步。谁让这份资产重新变得可用，谁就拿到了一个高频入口。
- **竞争风险**：Raindrop / Notion Web Clipper / Arc 的 pinned tabs 都在往这个位置切。Arc 甚至直接把"书签栏"重新设计成了 pinned 区。**Chromium 系原生体验的空档正在被填，窗口期有限。**

> ⚠️ **证据强度声明（必须诚实标注）**：以上痛点分析基于 **Chrome 书签 API 与原生 UI 的功能缺口推断 + 行业共识**，**尚未经过用户访谈验证**。在下述决策落地前，建议先做 **5–8 个 30 分钟访谈**（见 §9 Open Questions Q6）。我不会用"用户都说……"这种话给假设背书——**目前这些是假设，不是结论**。

## 2. Goals

### 用户目标（用户拿到什么）

| # | 目标 | 怎么知道成了 |
|---|---|---|
| G1 | 让收藏过的东西**重新被用到** | 周有效回访数（用户经插件打开书签的次数）≥ 3 次/周活用户 |
| G2 | **3 秒内**找回任意一条书签 | 搜索会话中位耗时 ≤ 3s；搜索后点击打开率 ≥ 45% |
| G3 | 让书签库**可治理**，而不是只能从头重建 | 30 天内 ≥ 25% 的用户处理过至少 1 条系统给出的建议（归类/去重/失效） |

### 业务目标

| # | 目标 | 怎么知道成了 |
|---|---|---|
| G4 | 建立高频入口（书签是浏览器内少见的"每天都在用"的场景） | 30 日留存 ≥ 35%；周活用户人均打开插件 ≥ 8 次 |
| G5 | 零迁移成本获客——装完立刻可见价值 | 安装后首个会话完成"打开一个书签"的比例 ≥ 70% |

### 目标的性质

注意 G1–G5 全是**结果指标**（outcome），没有一条是"做个 XX 功能"。功能是达成它们的候选手段，不是目标本身。

## 3. Non-Goals（明确不做什么）

| # | 不做 | 为什么不做 |
|---|---|---|
| N1 | **自建书签存储与云同步** | 这是本产品的**第一原则**。自建存储意味着：迁移成本、同步冲突、账号体系、隐私责任、数据丢失赔偿——全部成本换来的只是"能跨浏览器"。而 Chrome 账号同步已经免费给到了 90% 的价值。**数据源唯一真源 = Chrome 书签树。** |
| N2 | **网页正文归档 / 稍后读正文提取** | 那是 Pocket / Omnivore 的领域。正文存储涉及版权、容量、CDN 成本、以及一个我们不该碰的合规面。书签只存 URL 与标题。 |
| N3 | **跨浏览器 / 跨设备独立同步** | 与 N1 同源。v1 只做 Chromium 系（Chrome / Edge / Brave，API 兼容）。Firefox 的 `browser.bookmarks` 适配列入 v2 评估，不进 v1。 |
| N4 | **自动执行的书签整理** | ⚠️ **最重要的 Non-goal。** 直接改用户书签树是**高风险不可逆动作**，且会通过 Chrome 同步**污染用户所有设备**。v1 所有治理动作一律**建议式**：系统只提建议，用户逐条确认才写入。 |
| N5 | **协作 / 分享书签集** | 需要账号、权限、审核、内容治理。是另一个量级的产品，不是 v1 的范围。 |
| N6 | **替代浏览器 / 新标签页接管** | 与 Chrome 的"新标签页覆盖"能力重叠会引发与 Google 的平台紧张关系，且用户对新标签页接管极其敏感。v1 只做 popup + 一个完整管理页。 |
| N7 | **阅读器 / 笔记 / 标注** | 越界。书签的下游是读者自己的工具链。 |

## 4. 需求：痛点 → 功能映射

先把痛点钉死，再看功能怎么接。**每个 P0 都必须能回指一个具体痛点**——回指不到的不该进 v1。

| ID | 痛点 | 根因 | 对应需求 |
|---|---|---|---|
| **P1** | 收藏即遗忘，从不回看 | Chrome 从不主动展示书签；书签是被动资产 | R2 最近打开、R3 常用区、R12 回访提醒(v2) |
| **P2** | 组织成本 > 收益，分类法崩塌 | 手工维护文件夹是纯劳动，成本随条目线性增长 | R7 分类建议、R1 原树只读浏览 |
| **P3** | 搜不回来——**中文用户尤甚** | API 的 `search({title})` 要求**完全相等**；且它完全不认识拼音、繁简、多音字，更不处理输入法组合态 | **R4 中文优先的本地搜索**（全产品最重的一块技术投入） |
| **P4** | 不知道哪些链接已经死了 | 没有任何存活检测机制 | R9 失效检测(v1.5) |
| **P5** | 重复收藏，无人发现 | 同一文章不同 URL 形态（www / utm 参数 / 尾斜杠 / 锚点） | R8 重复检测(v1.5) |
| **P6** | 书签栏被当"常用区"用，最终溢出崩塌 | 常用站点只能靠"看得见"来维持，缺少更好的常用机制 | R3 常用区 |

## 5. User Stories

按优先级排序。Persona：**K** = 知识工作者，**G** = 通用用户。

### P0

- **US-01**（K/G）作为书签使用者，我想要在插件里按"I 上次用过"而非"我上次收藏"看到书签，**以便**我真正会用的东西浮上来，而不是最新收藏的那一堆。
- **US-02**（K/G）作为中文用户，我想要用**汉字、拼音全拼、拼音首字母、英文**中任意一种方式搜到我的书签（`设计灵感` / `sheji` / `sjlg` / `figma` 都能命中），**以便**我不必记得当年收藏时把它命名成了什么。→ 详见 **R4**
- **US-02a**（K）作为中文用户，我想要在**不记得词序**时也能搜到（输入 `灵感设计` 命中「设计灵感」），**以便**我不需要在脑子里还原当时的命名顺序。
- **US-02b**（K）作为中文用户，我想要**中英文混着打**（`figma设计`、`sj灵感`），**以便**我按最快的输入方式打字，而不是被迫切换输入法。
- **US-02c**（K）作为使用**繁体输入法**的用户，我想要搜 `設計` 也能找到「设计灵感」的书签，**以便**我不必为了搜索切换输入法。
- **US-02d**（K）作为用户，我想要在**中文输入法的拼音候选阶段不触发搜索**，**以便**我不会看到一屏由半截拼音造成的错误结果。
- **US-02e**（K）作为用户，当结果是**靠拼音**命中时，我想要看到"为什么它会出现"的提示，**以便**我不会觉得结果是乱来的。
- **US-03**（K）作为书签使用者，我想要在一个地方同时看到书签树和我自己的分类，**以便**我不用在十几个文件夹之间来回展开找一条链接。
- **US-04**（G）作为书签使用者，我想要点一条书签就直接在新标签页打开它，**以便**我不用先打开 chrome://bookmarks 再找一次。
- **US-05**（K）作为书签使用者，我想要插件在我于 Chrome 原生界面增删书签后立即反映变化，**以便**我不需要对着一份过期缓存做决策。
- **US-06**（K）作为书签使用者，当我的书签树读取失败或权限被拒时，我想要看到明确的原因和修复指引，**以便**我知道这不是"我的书签丢了"。

### P1

- **US-07**（K）作为书签使用者，我想要系统基于域名和标题给我归类建议、并让我逐条接受或忽略，**以便**我能整理书签但不用付出全手动分类的代价。
- **US-08**（K）作为书签使用者，我想要系统找出看起来重复的书签并让我确认合并，**以便**我不必自己逐条比对 URL。
- **US-09**（K）作为书签使用者，我想要对长期没打开过的书签做失效检测，**以便**我能清理死链而不错删还能用的内容。
- **US-10**（K）作为书签使用者，我想要在确认后一次性执行一批整理动作、并且能撤销最近一次操作，**以便**我敢下手清理。

### 边界与异常（必须覆盖）

- **US-11** 作为书签使用者，当我的书签库为空（新用户/新设备）时，我想要看到引导而非空白页，**以便**我知道该先收藏点什么。
- **US-12** 作为受管设备的用户，当某些书签被系统管理员锁定（`unmodifiable: "managed"`）时，我想要看到它们被明确标为不可改，**以便**我不会反复尝试一个注定失败的操作。
- **US-13** 作为书签量极大的用户（>5000 条），我想要插件在首屏 1 秒内可用，**以便**我不会因为卡顿而直接放弃。
- **US-14** 作为隐私敏感的用户，我想要在开启任何联网功能（失效检测 / 云端归类）前看到明确告知并单独授权，**以便**我的浏览位置不会被悄悄送出去。
- **US-15** 作为书签使用者，当我的整理动作因为同步冲突而部分失败时，我想要看到哪些成功了、哪些没成功，**以便**我能判断当前状态而不是以为全成了。

## 6. Requirements

### 6.1 关键技术约束（先读这节，它决定了什么做得成）

这些是我从 Chrome 官方 API 文档核实过的**硬事实**，直接改写了不少"想当然"的功能设计：

| # | 约束 | 影响 |
|---|---|---|
| **C1** | `chrome.bookmarks.search({title})` 要求标题**完全相等**，字符串形式只是 URL/标题的子串匹配；且它**完全不认识中文的拼音、繁简、多音字** | API 自带搜索**不可用** → 必须自建本地索引（R4）。**中文搜索能力只能自建，没有捷径**——这既是成本项，也是本产品最可能的差异化护城河 |
| **C2** | `bookmarks.update()` **只支持 title 和 url**，`onChanged` 也只在这两者变化时触发 | 无法通过 API 改"排序/标签"；顺序变更要靠 `onMoved` / `onChildrenReordered` |
| **C3** | ⚠️ **`dateLastUsed`（Chrome 114+）由 Chrome 自己在用户经原生 UI 打开书签时更新。扩展用 `tabs.create()` 打开 URL，Chrome 不认为是"使用书签"** | **"最近打开/常用"必须自建本地计数**，`dateLastUsed` 只能作为**初始种子**与**交叉校验**，不能作为唯一真源。**这是本规格最大的技术风险，见 Q1。** |
| **C4** | `dateLastUsed` **对文件夹无效**；`folderType`（Chrome 134+）区分 `bookmarks-bar` / `other` / `mobile` / `managed` | 文件夹维度没有"上次使用"信号，分类排序需另找依据 |
| **C5** | 不能修改根节点；不能重命名/移动/删除"书签栏""其他书签"两个特殊文件夹；受管节点 `unmodifiable: "managed"` 一律不可改 | 所有写操作必须先过滤 `unmodifiable` + `folderType === "managed"`，否则报错中断 |
| **C6** | `syncing`（Chrome 134+）标明节点是否同步到账号存储 | 可用于**如实**展示同步状态，而不是假装"已同步"（当前设计稿的"已同步"文案需要按此实现） |
| **C7** | 图标需 `"favicon"` 权限，取 `chrome-extension://<id>/_favicon/?pageUrl=…&size=32`；**对 `chrome://` 等特权 URL 无效** | 需兜底默认图标；content script 中使用还需声明 `web_accessible_resources` |
| **C8** | `"bookmarks"` 权限会触发"读取和更改您的书签"警告；`"favicon"` 在已申请 `tabs`/host 权限时不再额外弹窗 | 权限文案直接影响安装转化，见 Q2 |

> C3 是**整个产品的支点**。如果它成立，我们的"最近打开"就是全网唯一的；如果它不成立（例如未来 Chrome 改成 tabs 打开也算），我们的自建计数逻辑仍然有效，只是多了一层冗余数据。**无论哪种情况，自建计数都是对的技术选择。** 但必须在 1 个 spike 内验证清楚。

### 6.2 P0 · Must-Have（缺了就活不下去）

#### R1 · 书签树读取与本视图

**行为**：`bookmarks.getTree()` 一次性拉取整棵树，解析为内部扁平索引（含 `id / parentId / title / url / dateAdded / dateLastUsed / folderType / unmodifiable / syncing / path`）。60 秒软 TTL 缓存，配合 `onCreated` / `onChanged` / `onMoved` / `onRemoved` / `onChildrenReordered` 事件做增量失效。`onImportBegan` 期间**暂停一切写入建议**，`onImportEnded` 后重建索引。

**技术约束**：
- 树 → 扁平索引的构建必须放在 **Service Worker 启动时一次完成**，结果存 `chrome.storage.local`（MV3 的 SW 随时会被杀死，不能依赖内存状态）。
- 增量更新而非全量重建：单条 `onCreated` 只插入一个节点，不要重新 `getTree()`。
- 必须处理 `onRemoved` 对文件夹的语义——**文件夹递归删除只对文件夹本身触发一次通知，不通知其子节点**（Chrome 的行为），因此要按 `parentId` 级联清理索引。
- **`onImportBegan` 是必须实现的**：导入期间可能有数万条 `onCreated` 涌入，不暂停会导致索引风暴与 UI 卡死。

**验收标准**：
- [ ] Given 用户有 3000 条书签，When 首次打开 popup，Then 首屏可交互 ≤ 1s，完整索引 ≤ 3s
- [ ] Given 用户在 Chrome 原生界面删除一个文件夹（内含 50 条），When 回到插件，Then 这 50 条全部从视图消失，不残留
- [ ] Given 正在导入书签，When 打开插件，Then 不出现闪烁或卡死，导入结束后视图自动完整
- [ ] Given 书签树为空，Then 显示空状态引导（US-11），不显示报错

#### R2 · 最近打开

**行为**：按"用户最近一次通过书签**打开**的时间"倒序展示，展示相对时间（"12 分钟前"）。数据来源为**本地自建打开记录**（`chrome.storage.local`，保留最近 200 条），首次安装时用 `dateLastUsed` 回填种子数据。

**技术约束（关键）**：见 C3。本地记录结构：`{ bookmarkId, openedAt, openCount }`。打开动作由 R5 触发写入。**`dateLastUsed` 仅作种子，一旦有了本地记录就以本地为准。**

**验收标准**：
- [ ] Given 用户通过插件打开书签 A，When 再次打开插件，Then A 出现在最近打开列表首位
- [ ] Given 用户通过 Chrome 原生书签栏打开书签 B，When 打开插件，Then B 在 60s 内（或下次 SW 唤醒时）出现在列表（回落到 `dateLastUsed` 交叉校验）
- [ ] Given 一个全新安装、但 Chrome 里已有历史书签的用户，Then 列表用 `dateLastUsed` 回填，不显示"暂无数据"
- [ ] Given Chrome 版本 < 114（无 `dateLastUsed`），Then 降级为按 `dateAdded` 展示并标注来源，不报错

#### R3 · 常用区

**行为**：网格展示用户高频使用的书签。排序依据：本地 `openCount` 加权 + 最近打开时间衰减（近 30 天权重更高），取前 8–12 条。

**产品判断**：常用区的战略意义是**给用户一个比"往书签栏堆"更好的常用机制**（对应 P6）。因此它必须**不需要用户手动维护**——手动维护的常用区最终会退化成第二个书签栏。

**验收标准**：
- [ ] Given 用户 30 天内打开过书签 A 8 次、B 2 次，Then A 排在 B 之前
- [ ] Given 用户从未打开过任何书签（新装），Then 常用区回落到"书签栏前 8 条"，而非空白
- [ ] Given 用户没有任何书签，Then 整块隐藏，不留空框

#### R4 · 中文优先的本地搜索

> **为什么单独占一节**：我们的用户是中文用户，而**中文搜索的复杂度比英文高一个量级**——没有空格分词、有拼音、有繁简、有多音字、有输入法组合态。一句"N 条子串匹配"在英文下够用，在中文下会直接失效。这一节是本产品最不能省的技术投资。

##### R4.1 匹配能力矩阵（本节核心，工程照此实现）

| 档 | 输入示例 | 应命中 | 实现要点 |
|---|---|---|---|
| **P0 · 汉字子串** | `设计` / `灵感` / `设计灵感` | 标题含"设计灵感"的书签 | 基础 |
| **P0 · 词序无关** | `灵感设计` | 「设计灵感」 | 用户不记得词序 → 走 bigram 倒排，**不是整串匹配** |
| **P0 · 拼音全拼** | `sheji` / `shejilinggan` | 设计灵感 | 无声调，串内无分隔符 |
| **P0 · 拼音首字母** | `sj` / `sjlg` | 设计灵感 | 最高频的输入方式 |
| **P0 · 拉丁/英文** | `figma` / `FIGMA` | Figma | 大小写不敏感 |
| **P0 · 域名** | `dribbble` | dribbble.com 下全部书签 | 域名单独成通道，权重高于 URL 路径 |
| **P0 · 宽度/空白归一** | `Ｆｉｇｍａ`（全角）/ `figma `（尾空格） | Figma | NFKC + 折叠空白 |
| **P1 · 中英混排** | `figma设计` / `设计figma` | 「Figma 设计规范」 | 拆中文段与拉丁段，**段间取 AND** |
| **P1 · 拼音+汉字混排** | `sj灵感` / `sheji灵感` | 设计灵感 | 逐段尝试双解释（拼音 / 字面） |
| **P1 · 繁简通搜** | `設計` / `規範` | 设计规范 | 内置繁↔简双向映射 |
| **P1 · 多音字全读音** | `chongqing` / `zhongqing` | 重庆 | 索引期为常见多音字写入**全部读音变体** |
| **P1 · 声调容忍** | `shèjì` | 设计灵感 | 剥离 `U+0300–U+036F` 组合符 |
| **P1 · 标点宽松兜底** | `nodejs` | node.js | 查询与索引串各生成一份"去标点"形式做二次匹配 |
| **P2** | `sheji lginan`（错拼）、语义检索 | — | 编辑距离 ≤1（仅拉丁）/ embedding（R11） |

**P0 的判据**：P0 七条任缺一条，中文用户的核心使用路径就断了。它们**不是加分项，是入场券**。

**一个刻意的取舍 —— 拼音只做召回，不做排序锚。** `sj` 可能是"设计"，也可能是"审计""数据""时间"。若拿拼音当强锚，用户搜 `sj` 会被一堆拼音巧合的结果淹没。所以：**拼音的作用只是让"原本搜不到的东西变得搜得到"，排序永远以原文命中 + 用户行为为准。**

##### R4.2 查询归一化（所有通道共用同一入口，顺序不可跳）

1. `normalize('NFKC')` —— 全角转半角、兼容字符统一（`Ｆｉｇｍａ` → `Figma`）
2. 剥离声调组合符（NFD + 去除 `U+0300–U+036F`）
3. 繁体 → 简体映射（内置双向表）
4. 拉丁部分 `toLowerCase()`
5. 折叠空白（trim + 连续空白→单空格）
6. **刻意不做**：不删标点、不去连字符。因为 `c++`、`node.js`、`three.js` 这类技术名词的标点**是有语义的**，删掉会误召。→ 改为同时生成一份"去标点宽松形"，**只作为二次兜底匹配**，不进主匹配路径。

##### R4.3 索引结构（决定性能上限）

每个节点预生成**多通道 haystack**，落 `chrome.storage.local`：

```ts
type SearchIndexEntry = {
  id: string;
  title:  { raw: string; full: string; initials: string };  // "设计灵感" / "shejilinggan" / "sjlg"
  domain: { raw: string; full: string; initials: string };  // 同上三形式
  path:   { raw: string; full: string; initials: string };  // 文件夹路径拼接
  url:    string;                                            // 仅原文，不做拼音（URL 是拉丁语义）
  openCount: number;                                         // 复用 R3 行为信号
  lastOpenedAt: number | null;
  dateAdded: number;
};
```

- **全拼串不插分隔符**（`shejilinggan`）——用户输入时本来也不会打分隔符；但**同时保留音节边界数组**，用来派生首字母串（`sjlg`）和计算"前缀命中"。
- **多音字**：对常见多音字（约 200–400 个：重/行/乐/长/还/觉/得/调/差…）在生成 `full` 与 `initials` 时**追加全部读音变体**。单节点最多多出 2–3 个串，体积可控。生僻字与专名多音字不穷举，交 P2。
- **体积预算**：单节点索引 ≤ 300 字节；5000 条 ≈ 1.5MB（`storage.local` 默认 10MB，够用，**v1 不申请 `unlimitedStorage`**）。
- **拼音表预算 ≤ 400KB**（含多音字典）。这是 popup 冷启动的主要成本项，**必须实测**；若超预算或拖累 M5，裁剪到常用汉字集（3500 字）版本。选型见 Q11。

##### R4.4 排序模型（决定"好不好用"，比匹配更重要）

```
score = Σ( channelWeight × matchTypeWeight × positionBonus ) × behaviorBoost × lengthPenalty
```

| 因子 | 取值 |
|---|---|
| `channelWeight` | title `1.0` > domain `0.7` > path `0.45` > url `0.3` |
| `matchTypeWeight` | 原文（汉字/拉丁）`1.0` > 拼音全拼 `0.75` > 拼音首字母 `0.6` |
| `positionBonus` | 前缀命中 `1.3` / 词首命中 `1.15` / 中间命中 `1.0`；**首字母整串精确命中额外 ×1.2**（`sjlg` 完整匹配首字母串是强信号） |
| `behaviorBoost` | `1 + log10(1 + openCount) × 0.15 + 近 30 天衰减项`，**上限 ×1.6**（防止历史高频项永久霸榜，复用 R3 逻辑） |
| `lengthPenalty` | 标题长度 > 查询长度 × 6 时轻微降权（防长标题靠"包含"霸榜） |

**权重全部走可配置常量表**（`search/weights.ts`），不硬编码——上线后一定要调。

##### R4.5 性能与竞态（两条硬要求）

1. **性能分档**：≤ 2000 条走线性多通道扫描（简单、零维护，JS 下 <30ms）；> 2000 条启用 bigram 倒排索引（中文按字 bigram、拉丁按词）。**5000 条 p95 ≤ 80ms。**
2. **竞态必须处理**：输入 debounce 80–120ms，但**关键是不能让先发的查询覆盖后发的结果**。必须用递增 `queryId` 或 `AbortController` 丢弃过期响应。这是搜索实现最常见的 bug，且用户会**直接感知为"我打的字和结果对不上"**。→ 列为必测项（T-19）。

##### R4.6 交互细节

- `⌘K` / `Ctrl+K` 聚焦；`Esc` 清空并关闭；`↑`/`↓` 移动选中；`Enter` 打开；`⌘Enter` 新窗口打开。
- **匹配高亮必须能解释"为什么命中"**：原文命中直接高亮；**拼音命中时高亮对应汉字，并在结果行右侧给一枚轻量拼音提示**（`sjlg` → `设计灵感`）。没有这个提示，用户会觉得结果莫名其妙（US-02e）。
- ⚠️ **中文输入法组合期不得触发搜索**：必须监听 `compositionstart` / `compositionend`，**在 `compositionend` 才发起查询**。若按 `keydown` 搜索，会拿拼音候选阶段的字符去查（"sheji" 打到一半是 `s`/`sh`/`she`），产生满屏错误结果。**这是中文场景独有的坑，英文产品不会遇到。**
- **无结果**：显示"没有匹配的书签" + 「在网上搜索『xxx』」出口 + 末行一句提示"可输入拼音或首字母，如 `sjlg`"（**教用户用拼音，是提升 M2/M3 的关键**）。
- **搜索历史：不存。** 书签场景下重搜成本极低，而搜索历史是本产品最敏感的本地数据之一（等于用户意图日志）。**用隐私换那一点便利，不划算。**

##### R4.7 隐私

搜索与索引 **100% 本地**。查询串、拼音、结果一律不出设备。这条受**反指标 M13（外部请求数 = 0）**与**用例 T-18** 双重约束。

**验收标准**：见 **附录 C · 中文搜索验收用例表**（24 条，含负向、性能、竞态、输入法）。**P0 用例必须全绿才可发布。**

#### R5 · 打开书签

**行为**：点击一条书签 → 按用户偏好在新标签页打开（可选：前台/后台/新窗口）。同时写入本地打开记录（供 R2/R3 使用）。

**技术约束**：`chrome.tabs.create({ url, active })`。需过滤非 http(s) 协议（`javascript:` / `data:` / `file:` 需按用户设置决定是否允许，默认禁止 `javascript:`——它是 XSS 载体）。

**验收标准**：
- [ ] Given 用户点击一条书签，Then 新标签页打开该 URL，且本地打开记录更新
- [ ] Given 书签 URL 为 `javascript:...`，Then 默认不打开，并提示"该链接类型已被安全策略阻止"
- [ ] Given 用户设置为"后台打开"，Then 当前 popup 关闭后焦点仍在原标签页

#### R6 · 权限与失败态处理

**行为**：`bookmarks` 权限被撤销 / 读取失败时，显示明确原因 + 一键跳转权限设置页。受管节点（`unmodifiable: "managed"`）在 UI 中标注"由管理员管理"，并且**不提供**任何编辑入口。

**为什么是 P0**：书签是用户最敏感的数据之一。"插件打不开我的书签"如果被误解为"我的书签丢了"，会造成卸载 + 一星差评，且伤害不可逆。

**验收标准**：
- [ ] Given 用户撤销了 bookmarks 权限，Then 显示"需要书签访问权限"+ 可点击按钮直达 `chrome://extensions` 对应设置
- [ ] Given 某书签 `unmodifiable: "managed"`，Then 该条目带锁定标识且无编辑/删除入口
- [ ] Given 任何 API 调用抛错，Then 不在 UI 暴露原始错误字符串，转为可读文案 + 可选"复制诊断信息"

### 6.3 P1 · Nice-to-Have（v1.5 快速跟进）

#### R7 · 分类建议（建议式，不自动执行）

**行为**：基于**本地规则引擎**（域名映射 + 标题关键词 + 已有文件夹名相似度）为未归类的书签生成归类建议，用户逐条接受/忽略。

**关键产品原则**（对应 N4）：**只提建议，不自动写**。批量执行必须走 R10 的确认 + 撤销流程。

**v1.5 限制**：仅本地规则，**不接云端模型**。理由见 Q3——云端归类意味着把用户的完整浏览位置图谱送出本地，这个代价需要单独的产品决策，不能"顺手就做了"。

**验收标准**：
- [ ] Given 一条 `figma.com` 的书签且用户已有"设计工具"文件夹，Then 建议归入该文件夹
- [ ] Given 用户忽略某条建议 3 次，Then 同一规则不再对同类域名重复建议（避免骚扰）
- [ ] Given 建议采纳率 < 20%，Then 触发告警（说明规则质量不达标，见 M6）

#### R8 · 重复检测

**行为**：URL 归一化后聚类——去掉 `www.` 前缀、移除 `utm_*` / `fbclid` / `gclid` 等追踪参数、统一尾斜杠、丢弃 fragment。同组内保留 `dateAdded` 最早的一条，其余标为候选删除。

**验收标准**：
- [ ] Given `example.com/a`、`www.example.com/a`、`example.com/a?utm_source=x`，Then 三条聚为一组
- [ ] Given 两条 URL 仅 fragment（`#section`）不同，Then 视为重复
- [ ] **负向**：Given 两条 URL 仅查询参数值不同且该参数非追踪参数（如 `?id=1` vs `?id=2`），Then **不得**判为重复

#### R9 · 失效检测

**行为**：对**超过 30 天未打开**的书签做低频 HTTP `HEAD` 探测，标记 4xx / 5xx / DNS 失败为"可能失效"。用户可批量处理。

**技术约束与隐私设计（重点）**：
- ⚠️ 需要访问外部站点 → 必须使用 **`optional_host_permissions`**，**在用户主动开启该功能时才申请**，不在安装时索取。这是本产品最重要的隐私设计决策之一。
- 频率限制：每批 ≤ 20 条，间隔 ≥ 2s，仅在前台标签页空闲时执行；总配额上限防止触发目标站点的风控。
- **探测行为等价于"扩展代用户访问了这些 URL"**——目标站点会看到用户的 IP。这个事实必须在开启页用一句话说清楚。
- `HEAD` 不被支持时回落到 `GET` + 立即 `abort()`，不读响应体。

**验收标准**：
- [ ] Given 用户未开启失效检测，Then 扩展不发起任何外部网络请求（可用 DevTools Network 验证）
- [ ] Given 用户开启失效检测，Then 先弹出说明（含 IP 暴露告知）并请求权限，拒绝后功能不启用
- [ ] Given 一条书签返回 404，Then 标记为"可能失效"，但**不自动删除**
- [ ] Given 探测超时（5s），Then 标记为"无法确认"，区别于"已失效"（避免把慢站点误判为死链）

#### R10 · 批量执行与撤销

**行为**：批量整理动作（归类 / 删除重复 / 清理失效）走"预览 → 确认 → 执行 → 可撤销"四步。每次执行前在 `storage.local` 记录反向操作日志（保留最近 10 次）。

**为什么必须做**：这是让 N4 的"建议式"原则**真正可用**的前提。用户不敢下手清理，是因为怕不可逆。给了撤销他们才敢动。

**验收标准**：
- [ ] Given 用户接受 20 条归类建议，Then 全部执行成功或**全部回滚**（不允许半成功）
- [ ] Given 执行中途某条因受管节点失败（C5），Then 该条被跳过并在结果中单独列出，其余正常执行
- [ ] Given 用户点击撤销，Then 恢复上一次操作涉及的全部书签位置（10 分钟内有效）
- [ ] Given 撤销时某书签已被用户在别处删除，Then 跳过该条并如实报告，不静默失败

## 7. Success Metrics

### 北极星指标

**周有效回访数（Weekly Bookmark Revisits, WBR）** = 周活用户**通过插件打开书签**的总次数 ÷ 周活用户数

选它的理由：这个产品的全部存在意义是"让收藏过的东西被重新用到"。安装量、搜索次数都可能虚高，只有"真的点开并去了某个页面"是不撒谎的。

## 附录 A · 数据模型（草案）

```ts
type BookmarkNode = {
  id: string;
  parentId: string | null;
  title: string;
  url?: string;                    // 文件夹无 url
  isFolder: boolean;
  dateAdded?: number;
  dateLastUsed?: number;           // Chrome 114+，仅书签，仅原生 UI 打开时更新（见 C3）
  folderType?: 'bookmarks-bar' | 'other' | 'mobile' | 'managed';
  unmodifiable?: 'managed';        // 只读
  syncing?: boolean;               // Chrome 134+
  path: string[];                  // 面包屑，用于搜索与展示
};

type OpenRecord = {                // storage.local，最多 200 条
  bookmarkId: string;
  openedAt: number;
  openCount: number;
};

type Suggestion = {
  id: string;
  kind: 'categorize' | 'dedupe' | 'deadlink';
  bookmarkIds: string[];
  payload: Record<string, unknown>;
  status: 'pending' | 'accepted' | 'ignored';
  shownCount: number;              // 用于抑制重复建议（R7 验收项）
};

type UndoLog = {                   // storage.local，最多 10 条
  id: string;
  createdAt: number;
  ops: Array<{ type: 'move' | 'remove' | 'update'; before: BookmarkNode }>;
};

// SearchIndexEntry（多通道搜索索引）见 R4.3 —— 单节点 ≤ 300 字节，5000 条 ≈ 1.5MB
// SearchQuery（归一化后的查询）见 R4.2 —— 必须与索引走同一套归一化，否则必然对不上
```

> ⚠️ **归一化必须共用同一个函数。**索引侧与查询侧若各写一套（哪怕只差"要不要转小写"），就会出现"明明有这条书签却搜不到"的诡异 bug，且极难定位。→ 实现上应是一个被双侧调用的纯函数，并有单元测试锁住。
